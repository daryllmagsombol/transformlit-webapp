# PWA Offline Contracts

These contracts refine the approved decisions in `2026-10-01-pwa-design.md`; they do not expand product scope.

## Book download manifest and assets

- `GET /api/books/{bookId}/offline-manifest?contentVersion={integer?}` requires the current authenticated user and book read permission. It returns the latest authorized retained version when omitted, or the requested authorized retained version when provided. Unknown versions return `404` and unreadable books return `403`.
- `200 OfflineBookManifest` has required fields: `bookId: string`, `contentVersion: integer`, `title: string`, `author: string | null`, `description: string | null`, `coverAssetId: string | null`, `totalPages: integer`, `toc: TocEntry[]`, `pages: PageEntry[]`, and `assets: AssetEntry[]`. `TocEntry` is `{ id: string, title: string, pageNumber: integer, order: integer }`. `PageEntry` is `{ pageNumber: integer, imageAssetId: string, textLayerAssetId: string }`. Required arrays are complete and non-null; no published page may omit an image or text layer.
- `AssetEntry` is `{ assetId: string, kind: "COVER" | "PAGE_IMAGE" | "TEXT_LAYER", pageNumber: integer | null, mediaType: string, byteLength: integer, sha256: lowercase-hex-string }`. `pageNumber` is null only for the optional cover asset. Every page's two asset IDs resolve to entries for the same `bookId` and `contentVersion`.
- `GET /api/books/{bookId}/content/{contentVersion}/assets/{assetId}` returns the exact asset bytes with the manifest `mediaType`, `Content-Length`, and `ETag: "sha256-{sha256}"`. The URL is authenticated, version-pinned, and immutable; a missing version/asset returns `404`, incompatible access returns `403`, and bytes never vary within a version.
- Downloads do not call session-dependent reader endpoints, create reading sessions, or record page-view analytics. Clients stage a complete version as not-ready, verify item count/version/length/digest, then publish readiness atomically. A failed replacement retains the previous ready version.

## Annotation anchors and version provenance

- `PageTextAnchorV1` is `{ version: 1, page: positive integer, startOffset: nonnegative integer, endOffset: integer }`, validated with `endOffset > startOffset`. Offsets are zero-based UTF-16 code units in the exact page text-layer string for the named `contentVersion`; the anchor page must equal the operation's page. Server validation rejects missing/invalid anchors and unavailable versions; it never maps anchors to newer content.
- All six reader operations require the original `contentVersion`, whether or not they contain an anchor. Positioned annotation create/update requires `PageTextAnchorV1`; bookmark anchor is nullable. Notes remain part of highlight/annotation records; there is no standalone note operation.
- The server derives owner identity from authentication. Submitted account IDs never establish ownership.
- A mutation with an unavailable or incompatible content version returns a classified conflict; it is never silently remapped to current content.

## Operation envelope and results

- Transport is GraphQL `POST /graphql`, mutation `applyBookReaderOperation(input: ReaderOperationInput!): ReaderOperationResult!`; the browser uses the same-origin `/api/graphql` route. GraphQL input unions are unavailable, so `ReaderOperationInput` is a flattened typed envelope: `{ operationId: UUID, bookId: ID, contentVersion: positive integer, kind: OperationKind, entityId: ID | null, clientEntityId: UUID | null, targetKind: ANNOTATION | CONFLICT_COPY | null, baseRevision: integer | null, currentPage?: positive integer, scrollY?: finite nonnegative number | null, page?: positive integer, label?: string | null, color?: string | null, anchor?: PageTextAnchorV1 | null, text?: nonempty string, note?: string | null }`. Per-kind fields listed for that kind are required even though represented as optional fields in the flattened GraphQL input; all other kind-specific fields must be omitted. The authenticated subject, never a submitted account/user field, establishes ownership.
- Typed client operations are the union `ReaderOperation = ProgressSetOperation | BookmarkAddOperation | BookmarkRemoveOperation | AnnotationCreateOperation | AnnotationUpdateOperation | AnnotationDeleteOperation`. `OperationKind` is `PROGRESS_SET | BOOKMARK_ADD | BOOKMARK_REMOVE | ANNOTATION_CREATE | ANNOTATION_UPDATE | ANNOTATION_DELETE`. Variants are: `ProgressSetOperation { kind:PROGRESS_SET, entityId:null, clientEntityId:null, targetKind:null, baseRevision:integer>=0 (0 means no prior revision), currentPage:positive integer, scrollY:number|null }`; `BookmarkAddOperation { kind:BOOKMARK_ADD, entityId:null, clientEntityId:UUID, targetKind:null, baseRevision:null, page:positive integer, label:string|null, color:string|null, anchor:PageTextAnchorV1|null }`; `BookmarkRemoveOperation { kind:BOOKMARK_REMOVE, entityId:ID, clientEntityId:null, targetKind:null, baseRevision:positive integer }`; `AnnotationCreateOperation { kind:ANNOTATION_CREATE, entityId:null, clientEntityId:UUID, targetKind:null, baseRevision:null, page:positive integer, text:nonempty string, note:string|null, color:string|null, anchor:PageTextAnchorV1 }`; `AnnotationUpdateOperation { kind:ANNOTATION_UPDATE, entityId:ID, clientEntityId:null, targetKind:ANNOTATION|CONFLICT_COPY, baseRevision:positive integer, page:positive integer, text:nonempty string, note:string|null, color:string|null, anchor:PageTextAnchorV1 }`; `AnnotationDeleteOperation { kind:ANNOTATION_DELETE, entityId:ID, clientEntityId:null, targetKind:null, baseRevision:positive integer }`. Every variant also includes `operationId:UUID`, `bookId:ID`, and the original `contentVersion:positive integer`. The server validates UUID/ID formats, finite numbers, string constraints, page/version relationship, revision/nullability rules, target record type, and exact per-kind field presence before applying anything. All operations except `ANNOTATION_UPDATE` require `targetKind:null`; update requires an explicit target. `ANNOTATION` targets an ordinary highlight; `CONFLICT_COPY` targets a conflict copy by its ID and current revision.
- `operationId` is unique per authenticated subject and payload hash. Replaying the same ID and hash returns the durable prior result; reusing the ID with a different hash is rejected. Mutation and receipt commit atomically, and receipts have no short expiry while an operation can still be replayed.
- Deviation (deliberate): `INCOMPATIBLE_VERSION` and `ACCESS_DENIED` outcomes are terminal only until user/account/content state changes, so they are intentionally **not** recorded as receipts. A replay after access is granted or a compatible version becomes available is re-evaluated rather than frozen. Because no receipt exists for these outcomes, operation-ID reuse with a different payload is only rejected once an applied/conflict receipt exists for that ID; clients must still treat a terminal outcome as terminal until state changes.
- Concrete records: `BookmarkRecord { id:ID, clientEntityId:UUID|null, bookId:ID, page:positive integer, label:string|null, color:string|null, anchor:PageTextAnchorV1|null, contentVersion:positive integer, revision:positive integer, createdAt:ISO-8601 timestamp, deletedAt:ISO-8601 timestamp|null }`; `HighlightRecord { id:ID, clientEntityId:UUID|null, bookId:ID, page:positive integer, text:nonempty string, note:string|null, color:string|null, anchor:PageTextAnchorV1, contentVersion:positive integer, revision:positive integer, createdAt:ISO-8601 timestamp, updatedAt:ISO-8601 timestamp, deletedAt:ISO-8601 timestamp|null }`; `ConflictCopy { id:ID (immutable stable identity), operationId:UUID (originating operation), sourceEntityId:ID, bookId:ID, contentVersion:positive integer, page:positive integer, text:string, note:string|null, color:string|null, anchor:PageTextAnchorV1|null, revision:integer>=1, reason:STALE_REVISION|DELETE_VS_EDIT, createdAt:ISO-8601 timestamp }`; `clientEntityId` is null for migrated legacy rows whose provenance is unknown, and `ConflictCopy.anchor` is null when no trustworthy anchor exists (delete-vs-edit conflicts and legacy rows); the server never invents an anchor or a client identity to satisfy a non-null shape. A `DELETE_VS_EDIT` conflict copy records the current server annotation's honest content (its `page`/`text`/`anchor`), not fabricated content from the delete request. `ReaderTombstone { entityId:ID, kind:BOOKMARK|ANNOTATION, revision:positive integer, deletedAt:ISO-8601 timestamp }`; `ProgressRecord { bookId:ID, currentPage:positive integer, scrollY:finite nonnegative number|null, revision:nonnegative integer, lastReadAt:ISO-8601 timestamp }`. The server assigns each conflict copy an immutable ID and initial revision `1`; later conditional retarget updates increment that revision. A conflict copy is a first-class versioned annotation entity owned by the authenticated subject that submitted its origin operation; `id`, `operationId`, and `sourceEntityId` preserve stable identity and provenance. The server never accepts a client-supplied owner.
- An explicit retarget action creates a new idempotent `ANNOTATION_UPDATE` with `entityId=ConflictCopy.id`, `targetKind=CONFLICT_COPY`, and `baseRevision=ConflictCopy.revision`. The server conditionally applies it to that copy, increments the copy revision, and returns normal `APPLIED` semantics. A stale retarget returns normal `CONFLICT` with the unchanged current `ConflictCopy` as `serverValue` and a non-null new conflict copy containing the offline edit; neither value is overwritten silently. Clients never automatically retarget: the user must choose the copy and revision. Ordinary highlight updates use `targetKind=ANNOTATION`.
- Every response has `operationId` and exactly one `result.kind`: `APPLIED { entityId:ID, revision:positive integer, receiptId:ID }`; `CONFLICT { entityId:ID, serverRevision:positive integer, serverValue:BookmarkRecord|HighlightRecord|ConflictCopy|ProgressRecord, conflictCopy:ConflictCopy|null }`; `INCOMPATIBLE_VERSION { requestedContentVersion:positive integer, supportedContentVersions:positive integer[] }`; or `ACCESS_DENIED { resourceId:ID, reason:string }`. Stale annotation edits/retargets require non-null `conflictCopy`; progress/bookmark conflicts may return null. Incompatible-version and access-denied results are terminal until user/account/content state changes. Transport/server failures do not acknowledge or discard the queued operation.
- Operations for one entity are ordered. Deletes preserve tombstone/order protection; a delayed create/update cannot resurrect a deleted record.

## Snapshot consistency and tombstones

- Snapshot transport is GraphQL `POST /graphql`, query `bookReaderAnnotationSnapshot(bookId: ID!): BookReaderAnnotationSnapshot!`; browser same-origin route is `/api/graphql`. Exact response: `{ bookId:ID, snapshotRevision:nonnegative integer, annotations:(BookmarkRecord|HighlightRecord)[], tombstones:ReaderTombstone[], conflictCopies:ConflictCopy[] }`. Each `ConflictCopy` includes its current `revision`.
- `snapshotRevision` is a monotonically increasing per-book annotation sequence. All three collections, including conflict-copy revisions, represent one transaction boundary and are covered by that same revision. Conflict-copy retarget updates advance the annotation snapshot sequence. The snapshot excludes progress. Reading progress remains a separate revisioned `readProgress(bookId)` query/operation and never increments or affects annotation `snapshotRevision`.
- Clients merge by stable entity ID/revision. Pending local operations remain authoritative over older snapshot state, and snapshots do not silently rebase them. Tombstones prevent stale records or retries from resurrecting deleted entities.
- An operation conflict pauses subsequent operations for that entity until explicit resolution.

## Account lifecycle, lock order, and failure classification

- States are `SIGNED_OUT`, `ACTIVE(subject)`, `OFFLINE_ESTABLISHED(subject)`, `SYNCING(subject)`, `AUTH_REQUIRED(subject)`, `SIGN_OUT_PENDING(subject)`, and `DEFERRED_LOGOUT(subject)`. Records/outbox are keyed only by immutable `subject`; access tokens are never persisted.
- Allowed transitions: `SIGNED_OUT -> ACTIVE(subject)` only after successful authentication and with no deferred logout; `ACTIVE(subject) <-> OFFLINE_ESTABLISHED(subject)` as connectivity changes while retaining the same local identity; `ACTIVE -> SYNCING -> ACTIVE`; `ACTIVE|SYNCING -> AUTH_REQUIRED` on genuine HTTP 401; `AUTH_REQUIRED(subject) -> ACTIVE(the same subject)` only after successful same-subject reauthentication; `ACTIVE|OFFLINE_ESTABLISHED|AUTH_REQUIRED -> SIGN_OUT_PENDING` under the lifecycle lock; `SIGN_OUT_PENDING -> SIGNED_OUT` only after drain or explicit discard, durable barrier, old-account cleanup, and remote invalidation; `SIGN_OUT_PENDING -> DEFERRED_LOGOUT` on network/remote invalidation failure; `DEFERRED_LOGOUT -> SIGNED_OUT` only after old-session invalidation completes. A new subject cannot activate until the old logout barrier completes.
- Cross-tab locks are acquired in strict order: lifecycle lock -> per-account sync lease -> per-entity operation lock. Switching and sign-out take the lifecycle lock first. Lifecycle work freezes writes, drains or obtains explicit discard consent, persists the barrier, invalidates late sync/auth results, invalidates the remote session or defers logout, clears the old account, then releases the lock.
- Network/5xx failure preserves all local content and pending work and pauses synchronization. Genuine 401 requires same-subject reauthentication. Subject mismatch, revision conflict, incompatible content version, access denial, and invalid operation are distinct actionable outcomes; none authorize token persistence, silent rebase, or cross-account replay.

## Quota, incomplete downloads, conflicts, and sign-out UX

- Request persistent storage when supported and report estimated usage/quota. On quota or write failure, retain the previous ready content and all pending edits; never automatically evict outbox records.
- An interrupted/incomplete download is visibly incomplete and cannot be opened as ready. It can be retried or discarded without deleting annotations/outbox state.
- Conflicts visibly preserve both versions and offer explicit server-choice, keep-as-conflict-copy, or retargeted-edit resolution. Permanent failures expose retry/recovery/discard choices appropriate to the classification.
- Sign-out/account-switch is blocked while pending work exists until synchronization succeeds or the user explicitly confirms discard. Offline/failed remote logout leaves a durable logout barrier and prevents account activation until server-session invalidation completes.

## Compatibility window

- The client, API operation envelope, and IndexedDB schema carry explicit versions. A client may read/write only server-supported operation versions; incompatible operations are held for recovery and are never dropped or guessed into a new shape.
- IndexedDB upgrades are transactional and preserve content, pending operations, receipts, and barriers across supported client upgrades and rollbacks. Service-worker cache cleanup is independent of IndexedDB cleanup.
- The supported window is the current deployed client plus the immediately previous still-open client during a rolling deployment. The API accepts both versions during that overlap; deploys must not remove an operation/schema version until the prior client is outside this overlap and no corresponding work can remain in replay.

## Integration fixture contract (prepared in Task 1B)

- Seed two distinct accounts with stable test-only credentials and immutable subjects; never share one account's content or queued work with the other.
- Seed a published, multi-page book readable by the first account with complete metadata, TOC, rendered page assets, text layers, and at least two retained content versions.
- Seed a restricted book that the first account cannot read, so authorization is tested independently of download completeness.
- Keep fixture setup isolated to the owned disposable test database and emit any generated credentials/output only inside ignored repository test artifacts.
